# Codex 게임 개발 지침

이 문서는 이 저장소에서 작업하는 Codex의 기본 지침이다. 사용자의 최신 명시적 요청을 우선하고, 아래 기본 틀을 임의로 변경하지 않는다.

## 프로젝트 목표
- C++·OpenGL 기반의 실시간 렌더링 게임을 제작한다.
- 장르는 오픈 월드 RPG이며, 시각 표현은 쿼터뷰 2.5D이다.
- 소울류 다크 판타지, 암울하고 희망이 희박한 분위기, 육체 변이와 코스믹 호러를 중심으로 한다.
- 핵심 주제는 감염체에 의존해 생존하는 새로운 인류와 인간성의 정의이다.
- 세계관과 메인 퀘스트 기본 틀은 [게임 개발 기본 기획](docs/GAME_DESIGN.md)을 참조한다. 관련 기획·구현 전에 필요한 부분을 읽는다.

## 사용자와의 작업 방식
- 한국어로 답한다. 질문에는 이유와 원리, 현재 프로젝트에의 적용, 앞으로의 권장 단계를 충분히 설명한다. 불필요하게 같은 내용을 반복하지 않는다.
- 작업 전에는 **변경 위치 → 변경·추가할 내용 → 목적과 예상 동작**을 보고한다. 파일·함수·클래스 단위로 구체적으로 설명하되, 사용자가 요청하기 전에는 구현 코드 전체를 나열하지 않는다.
- 단순히 “이동을 구현한다”라고 하지 말고, 예를 들어 “SimpleGame.cpp의 입력 콜백에서 키 상태를 전달하고 Game의 업데이트에서 이동을 계산한다”라고 설명한다.
- 설명 요청을 코드 수정 요청으로 간주하지 않는다. 수정이 요청되면 위 보고 후 승인된 범위에서 진행한다. 매번 추가 확인을 요구하지 않는다.
- 완료 후 실제 변경사항과 사용자가 직접 확인할 항목을 보고한다.
- **기본적으로 빌드, 실행, 테스트 및 실행 결과 확인을 수행하지 않는다. 사용자가 직접 담당한다.** 사용자가 요청하거나 특별한 검증 필요성이 있는 경우에만 다루고, 예외가 필요하면 먼저 이유를 설명한다. 문맥 파악을 위한 소스·설정 읽기는 가능하다.
- 토큰 절약을 고려해 관련 파일부터 좁게 탐색한다. 불필요한 전체 탐색·대규모 리팩터링·반복 검증을 피한다. 필요한 설명의 충실함은 유지한다.
- 기존 사용자 변경, IDE 파일, 빌드 결과물을 임의로 정리하거나 되돌리지 않는다. 커밋·푸시는 요청받았을 때 수행한다.

## 현재 코드 기반과 구현 방향
- Visual Studio 솔루션: SimpleGame.sln, C++ 도구 집합 v143, GLEW·freeglut 사용.
- SimpleGame.cpp: 창과 입력. Game.h/.cpp: 진행·UI. VillageArt.cpp: 마을과 인물. Renderer.h/.cpp 및 RendererShaders.h: 도형·재질·후처리·한국어 글꼴. 이전 SolidRect 셰이더 파일은 현재 렌더러에서 사용하지 않는다.
- 현재 튜토리얼 코드가 구현되어 있으며 상세 현황은 docs/PROTOTYPE_IMPLEMENTATION.md를 따른다. 아래 본편 확장 방향 중 미구현 기능까지 완료되었다고 가정하지 않는다.
- 입력, 시간 기반 게임 상태 업데이트, 렌더링을 분리한다. Game이 전체 흐름을 연결하고 Player, World, Camera가 책임을 나눈다.
- 월드 좌표와 화면 좌표를 분리한다. 카메라 추적, 앞뒤 가림, 높이와 충돌을 고려한다.
- 넓은 월드는 청크 단위 관리와 화면 밖 렌더링 제외를 단계적으로 도입한다. 처음부터 복잡한 스트리밍 시스템을 만들지 않는다.
- 타일맵·오브젝트 정의와 배치·스프라이트 메타데이터는 JSON 등의 외부 데이터로 관리하는 방향을 기본으로 한다. 실제 이미지 픽셀은 별도 이미지 파일에 둔다.
- 데이터 흐름은 제작 → 파일 저장 → 로딩·유효성 검사 → 월드 구성 → 렌더링으로 설계한다. 리소스 중복 로딩을 피하고, 원본 콘텐츠와 플레이 중 변경된 세이브 상태를 구분한다.
- 우선 작은 외부 맵의 표시, 임시 플레이어 이동, 카메라를 구현한 뒤 청크·충돌·NPC·전투·아이템·저장으로 확장한다.
- 2D 스프라이트 기반인지 실제 3D 모델 기반인지, 구체적인 데이터 스키마와 라이브러리, 전투 규칙은 아직 미정이다. 2D 기반은 기존 제안이며 확정으로 취급하지 않는다.

## 기존 분석에서 발견한 사항
아래는 이전 소스 분석 결과다. 수정 시 현재 코드를 다시 읽고 적용 여부를 판단한다. 자동 수정 지시는 아니다.
- CompileShaders의 GLuint 반환형에 실패값 -1을 사용하여 초기화 성공 검사에 잘못 통과할 가능성.
- ./Shaders 상대 경로에 따른 실행 작업 디렉터리 의존.
- gitignore 파일에 선행 점이 없고 IDE 캐시와 빌드 산출물이 Git에 추적되어 있음.
- 창 크기 변경 처리, 시간 기반 업데이트, OpenGL 자원 해제 보완 필요.

## 기획 변경 원칙
- 확정된 목표·세계관과 제안 수준의 세부 설정을 구분한다.
- 세계관의 중심을 단순한 감염 제거 또는 명백한 선악 대결로 축소하지 않는다.
- 새 제안은 기존 틀과의 관계를 설명한다. 사용자 결정으로 기획이 변경되면 관련 문서도 일관되게 갱신한다.

## 최신 튜토리얼 요구사항
- 시작은 파괴된 마을. 생존 인물은 주인공과 죽기 직전 감염자 한 명이며 시체가 배치된다.
- WASD 이동, 2.5D 쿼터뷰, 적절한 상호작용키와 작은 퀘스트, 5분 이내 의도된 진행을 목표로 한다.
- 실제 게임 화면에서 세계관 분위기를 표현해야 한다. 설계만으로 렌더링 완료를 주장하지 않는다.
- 튜토리얼의 최신 범위와 구현 계획은 docs/TUTORIAL_LEVEL.md를 따른다. 이전 치료소 시작안보다 우선한다. 후속 전투 레벨은 docs/LEVEL_ONE.md를 따른다.

## 프로토타이핑 요청 해석
- 사용자가 프로토타이핑을 요청하면 설계 문서 작성뿐 아니라 실제 게임 코드와 필요한 데이터를 구현한다. 설계만 작성하고 종료하지 않는다.
- 현재 첫 프로토타입은 외부 에셋 없는 2D 도형 기반 쿼터뷰로 구현한다. 본편 전체 에셋 방식 확정을 의미하지 않는다.

## 시각 개선판의 현재 구조
- UI와 대사는 한국어를 기본으로 한다. 대사는 SimpleGame/Data/dialogue.ko.txt에 외부화했다.
- 현재 코드 역할: Game.cpp는 게임 진행·한국어 UI, VillageArt.cpp는 환경·캐릭터 표현, Renderer.cpp와 RendererShaders.h는 렌더링·후처리·한글 글꼴을 담당한다.
- 튜토리얼 맵은 52×40으로 확장했다. 필수 진행 5분 이내 목표와 생존 인물 두 명 조건은 유지한다.
- MSAA·FXAA·블룸·재질 표현과 분절형 2D 애니메이션이 코드에 추가되었다. 외부 스프라이트나 3D 모델이 있다고 가정하지 않는다.
- 구현의 실행 검증은 사용자가 담당한다. 상세 현황은 docs/PROTOTYPE_IMPLEMENTATION.md를 따른다.


## 코드 컨벤션
- 직접 작성하는 C++ 코드는 루트 .clang-format을 따른다. 외부 Dependencies 코드는 포맷하지 않는다.
- 들여쓰기 4칸, 탭 대신 공백, 중괄호는 별도 줄(Allman), 한 줄은 100자를 기준으로 한다.
- 여러 실행문을 한 줄에 모으지 않는다. 짧은 조건문과 반복문에도 중괄호를 사용한다.
- 함수 사이와 의미가 다른 처리 단계 사이에 빈 줄을 넣는다. 과도한 연속 빈 줄은 피한다.
- RendererShaders.h에 포함된 GLSL도 줄바꿈·들여쓰기를 동일하게 정리한다. 코드 문자열의 의미는 변경하지 않는다.
- include 순서는 미리 컴파일된 헤더 사용을 고려해 임의로 정렬하지 않는다.

## 첫 전투 레벨 — 2026-09-14
- 튜토리얼 이후 경험치를 모으고 능력치를 배분하는 랜덤 사냥터를 구현한다. 실제 구현 범위·조작·조정 수치는 docs/LEVEL_ONE.md를 따른다.
- LevelOne은 전투·아이템·UI, RpgStats는 성장 수치, RandomLevelMap은 연결된 방과 통로, ModelCache는 도형 모델 캐싱을 담당한다. Game은 튜토리얼과 첫 레벨 사이 흐름을 연결한다.
- 첫 레벨 모델은 도형으로 최초 생성해 Data/Cache/level1_models.bin에 저장한다. 다음 실행에서는 유효한 캐시를 읽고 생성 과정을 건너뛴다. 모델 형상 변경 시 CacheVersion도 올린다.
- 불꽃·물결은 RendererShaders.h의 시간 기반 셰이더로 표현한다. 실제 외부 스프라이트/3D 모델이 추가되었다고 가정하지 않는다.
- 랜덤 맵은 모든 이동 가능 바닥을 연결하고, 생성 후 도달 가능 영역을 조사해 단절을 보정한 뒤 적을 배치한다. 얕은 물과 장식이 통로를 끊지 않게 한다.
- 첫 목표의 레벨 3, 레벨업당 2포인트와 세부 전투 수치는 조정 가능한 프로토타입 초기값이다. 본편 규칙 확정으로 취급하지 않는다.
- 경험치·능력치·소지품 유지는 동일 실행의 사망/맵 재생성에 한정한다. 재실행 간 플레이 세이브는 미구현이며 모델 캐시와 구분한다.
- 이번 추가 구현도 빌드·실행·테스트는 사용자가 담당한다. 소스 추가만으로 실행 검증 완료를 주장하지 않는다.

## Actor 기반 화면 구성 — 2026-09-21
- 화면에 배치하는 객체는 Actor 기반으로 관리한다. 상세 구조와 적용 범위는 docs/ACTOR_ARCHITECTURE.md를 따른다.
- Actor는 공통 위치·활성·표시·제거 상태와 Update/Render 진입점을 제공한다. 새 배치 객체는 Actor를 상속하고 OnUpdate/OnRender를 구현한다.
- Scene은 프레임 안에서만 Actor 참조를 모아 바닥·그림자·월드·효과·오버레이·UI 순서를 처리한다. 월드 객체는 Depth로 정렬하고 UI는 후처리 뒤에 그린다.
- Actor 소유는 Game/LevelOne의 멤버와 컨테이너에 유지한다. Scene은 비소유 목록이며 렌더링 중 컨테이너를 변경하지 않는다. 프레임을 넘겨 vector 원소의 포인터를 캐시하지 않는다.
- 플레이어, 튜토리얼 Object·Footprint, 첫 레벨 Enemy·Drop·Prop·FloatingText가 Actor 경로를 사용한다. 지형·분위기·HUD는 CallbackActor로 묶는다. 내부 도형·타일·문자까지 각각 독립 Actor라는 의미는 아니다.
- SetVisible은 표시만, SetActive는 업데이트와 표시를 중단한다. 게임 판정에서도 활성·제거 상태를 확인한다. 적 사망 후 시체 표시는 Actor 제거와 구분한다.
- 실제 OpenGL 처리와 후처리는 Renderer, 재사용 모델 데이터는 ModelCache가 담당한다. 기존 표현 함수는 Actor 내부에서 호출할 수 있으나 화면의 배치 객체를 Actor 경로 밖에서 직접 순회 렌더링하지 않는다.
- 부모-자식 변환, 그룹 이동·회전·스케일, 전체 Scene 소유권 이전은 아직 구현하지 않았다. 지형·분위기·HUD 묶음은 기존 좌표계를 사용한다.
